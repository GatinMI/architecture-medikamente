# Что улучшить: защита данных, тегирование, меры по потокам

## 1. Данные для защиты и способы защиты

| Данные | Категория | Способ защиты | Как применяем |
|---|---|---|---|
| ФИО | ПД | шифрование + обфускация + псевдонимизация | шифрование at rest в системе; инициалы в UI и отчётах; `patient_id` в аналитике |
| Дата рождения | ПД | шифрование + обфускация | шифрование at rest; в отчётах - обобщение (год/возрастная группа) |
| Телефон, e-mail | ПД | шифрование + обфускация | шифрование at rest; маска в UI (`+7 *** *** 12-34`); в аналитике - псевдонимизация |
| Адрес прописки | ПД | шифрование + минимизация | шифрование at rest; собирать только если нужно для процесса |
| Место работы/учёбы | ПД | Data Minimization | убрать из формы, если процессы не используют; если нужно - шифрование at rest |
| Хронические заболевания (расширенная форма) | особая категория (здоровье) | шифрование + отдельное согласие + псевдонимизация | доступ только лечащему врачу; отдельное согласие (152-ФЗ); в ML/BI - псевдонимизация |
| Диагноз, заключения, медкарта | особая категория (здоровье) | шифрование + RBAC + аудит | шифрование at rest; доступ только лечащему (ABAC: `врач = лечащий`); аудит и версионирование обращений |
| Результаты анализов | особая категория (здоровье) | шифрование + тегирование + псевдонимизация | тег `health.lab_result`; шифрование at rest; в аналитике - псевдонимизация |
| Договоры (PDF) | ПД | шифрование | хранение в личном кабинете пациента, а не на общем диске; шифрование at rest |
| Платежи (услуга, сумма, способ) | финансовые | шифрование + минимизация | шифрование at rest, тег `fin.payment`; данные карт не храним (PCI DSS) - только ID транзакции |
| Зарплата, паспорт, СНИЛС, адрес (кадры) | особая категория (кадры) | шифрование + строгий доступ | 1С в серверном режиме; доступ только бухгалтерии (RBAC); тег `hr.salary`, аудит доступа |
| Цены, реквизиты поставщиков | корпоративные | доступ по ролям | тег `corp.financial`; доступ - бухгалтерия и склад |
| Расписание, записи к врачу | внутренние | обфускация | инициалы вместо полного ФИО; тег `internal` |

## 2. Механизм тегирования данных

Классификация - 4 уровня, уровень = тег:

| Уровень | Теги | Что к ним относится |
|---|---|---|
| Публичный | `public` | открытые данные (сайт, прайс) |
| Внутренний | `internal` | расписание, записи, корпоративные данные |
| Конфиденциальный | `pii.full_name`, `pii.contact`, `pii.address` | персональные данные пациентов |
| Чувствительный | `health.*`, `hr.*`, `fin.*` | данные о здоровье, кадры, финансы |

Как устроен механизм:

1. **Где живут теги.** В каталоге данных (метаданные): каждое поле схемы в новых системах (CRM, портал, 1С, лаборатория) имеет тег. Для легаси-файлов (Excel, сканы) тег указывается в реестре каталога: `Patients.xlsx → pii.full_name, pii.contact`.
2. **Кто назначает.** Автоматически - при миграции Excel/1С каталог помечает поля по именам колонок и паттернам (ФИО, телефон, дата рождения, диагноз). Для новых полей - вручную: тег обязателен в словаре данных, без тега релиз не собирается.
3. **Что делают с тегами:**
   - **Доступ** - политики RBAC/ABAC: роль видит поля с тегами по матрице (врач - `health.*` своих пациентов, кассир - `fin.payment`, никто - `hr.*`);
   - **DLP** - правила для почты, флешек и печати: блокируются письма с тегируемыми данными, которые политика не разрешает;
   - **CI/автопроверка** - релиз автоматически проверяется на работу с тегируемыми данными: код/запрос, обращающийся к `pii.*` или `health.*` без заявленной разрешённой роли, не проходит сборку;
   - **Мониторинг и алерты** - SIEM собирает логи обращений к тегируемым данным; алерт на нетипичное (ресепшен открыл 50 медкарт за час, выгрузка именованного Excel ночью);
   - **Data Lineage** - тег наследуется при трансформациях (Excel → отчёт, 1С → 1С), поэтому видно, куда «уплыли» именные данные.

Инструменты: каталог данных + lineage (DataHub/Apache Atlas, OpenLineage), DLP для почты и рабочих мест (например, Kaspersky DLP, MailGuard), AD + RBAC/ABAC с MFA, SIEM (Wazuh/Graylog) для алертов, AES-256 at rest и TLS 1.2+ in transit, шифрование дисков серверов.

## 3. Меры по каждому этапу потоков

Всё перечисленное отмечено на To-Be листах диаграмм в `dfd/`.

| Этап потока | Что использовать |
|---|---|
| Сбор (ресепшен) | согласие (152-ФЗ); Data Minimization; отдельное согласие на особые категории; портал - HTTPS (TLS) |
| Хранение | шифрование at rest (AES-256); 1С из файлового режима в серверный; сервер в серверном помещении, разделение зон |
| Передача внутри | TLS на всех каналах; сегментация сети |
| Доступ | RBAC/ABAC «need to know»; MFA; процедура выдачи/отзыва доступа |
| Почта (Exchange) | TLS каналов; DLP исходящей почты; данные пациента в теле письма - только ссылки на ЛК |
| Лаборатория | API: HTTPS + OAuth2-токены; псевдоним пациента в заказе; целостность сообщения (чексаум); аудит вызовов |
| Бухгалтерия / ФНС | отчётность через ТКС (TLS + электронная подпись); внутренние отчёты - агрегированные |
| Аналитика / BI / ML | псевдонимизированные выгрузки (`patient_id`); агрегация; без именных ПД в отчётах для руководства |
| Аудит | централизованный логинг обращений к тегируемым данным; SIEM; алерты на нетипичные действия |
| Удаление | политика хранения (retention); процедура на запрос 152-ФЗ: прекращение обработки и удаление, включая из бэкапов |
| Организация | политика классификации данных, обучение сотрудников, план реагирования на инциденты |
