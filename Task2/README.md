# Задание 2. Проектирование решения (Privacy by Design)

`c4-context-to-be.drawio` - C4-контекст целевого состояния «Медикаменте».

Центральный блок - единая система (порталы для клиентов и ресепшена, CRM, электронные медкарты, биллинг). Зелёным выделены **новые блоки**, которые обеспечивают принципы Privacy by Design во всех остальных блоках системы как общие компоненты: каждый модуль (портал, CRM, медкарты, биллинг) использует их, а не реализует защиту сам.

## Новые блоки для приватности

| Блок | Принцип Privacy by Design | Что делает |
|---|---|---|
| IAM (MFA, RBAC/ABAC) | least privilege, защита по умолчанию | единый центр удостоверений; доступ к данным по ролям и тегам: врач видит только своих пациентов, кассир - только платежи, бухгалтер - ЗП/кадры |
| Каталог данных и тегирование | классификация данных, Data Minimization, Data Lineage | полевые теги `pii.*`, `health.*`, `hr.*`, `fin.*`; поле без тега не принимается в схему; теги наследуются при трансформациях - новые интеграции не нужно перевалидировать |
| KMS (управление ключами) | шифрование по умолчанию | ключи вынесены из хранилищ данных; AES-256 at rest, TLS 1.2+ in transit на всех каналах (включая API лаборатории и платёжный шлюз) |
| Аудит и мониторинг (SIEM) | подотчётность, прозрачность | централизованный логинг обращений к тегируемым данным, алерты на нетипичные действия; в As-Is доступа «кто чью медкарту открыл» ответить было нельзя |
| DLP | защита от утечек | почта, конечные точки, печать: правила по тегам; данные пациента в теле письма не уходят - ссылка на ЛК |
| Аналитический слой (data lake) | псевдонимизация, разделение ответственностей | см. ниже |

## Аналитический слой

- В lake попадают **псевдонимизированные выгрузки** (`patient_id`), а не именные данные; соответствие псевдоним ↔ пациент хранится отдельно и доступно узкой роли - это и есть аналитическая работа с данными при соблюдении Privacy by Design (BI, ML, LLM на этих данных).
- Теги наследуются из операционного слоя (Data Lineage), поэтому аналитический слой «знает» чувствительность каждого поля.
- Операционные и аналитические данные изолированы: компрометация lake не раскрывает операционные данные пациентов и наоборот.
- Потребители: бизнес-аналитик (отчёты, ML/LLM-модели) и руководство (агрегированная аналитика без именных ПД).

## As-Is → To-Be: что закрывает каждый блок

Проблемные зоны из `Task1/problems.md`:

- № 1, 4, 5 (данные на общем диске, нет ролей, нет аудита) → IAM + каталог/тегирование + SIEM;
- № 3 (нет шифрования at rest) → KMS;
- № 8 (почта без DLP) → DLP;
- № 2, 14 (нет классификации, аналитика на именных Excel) → каталог/тегирование + аналитический слой;
- № 12 (лаборация через бумагу/телефон) → API-интеграция с лабораторией (псевдоним пациента, OAuth2, целостность).

## MVP (первый срез целевой архитектуры)

Портал клиента (самостоятельная запись, свои данные в ЛК) + портал ресепшена (отслеживание записей, напоминания за день до приёма) + уведомления (push в мобильное приложение, голосовой робот). Остальные блоки целевого состояния добавляются по мере выхода на финальное состояние (год).

Детальная структура самих компонентов (C2/C3) - в следующих заданиях (C2 движка классификации - в Task6).
