# Задание 3. Оценка Data Encryption at Rest and In Transit

## Что защищаем и почему

«Медикаменте» работает с тремя группами данных, каждая из которых требует своей защиты:

* персональные данные пациентов и особые категории (данные о здоровье) - 152-ФЗ, 323-ФЗ (врачебная тайна);
* платёжные данные - требования эквайринга (PCI DSS): сам PAN карты хранить нельзя;
* корпоративные данные (цены, ЗП, реквизиты) - коммерческая тайна, риски при увольнении сотрудников и утечках.

Кроме чувствительности, данные нужно развести по **состояниям**, потому что защищаются они по-разному:

| Состояние | Что это | Главная угроза |
|---|---|---|
| At rest | данные на дисках: Excel-файлы, 1С-базы, сканы, БД, бэкапы | доступ к диску/файлу (потеря сервера, ушёл сотрудник, скопировал файл домой) |
| In transit | данные в движении: LС, TCP/IP до ККМ, OLE между 1С, API лаборатории, e-mail | перехват в сети, подмена, подглядывание в локальной сети |
| In use | данные в оперативной памяти приложений и на экранах | скриншоты, общий доступ к приложению, чтение памяти, «плечевые» атаки |

## 1. Классификация данных

Классы совпадают с тегами из Task1 (`pii.*`, `health.*`, `hr.*`, `fin.*`, `corp.financial`, `internal`):

| Класс (тег) | Примеры | Чувствительность | Профиль риска | Где бывает |
|---|---|---|---|---|
| `health.sensitive` | медкарты, диагнозы, заключения | максимальная (особая категория ПД, 152-ФЗ ст. 10) | утечка через общий диск, доступ «всем подряд», сканы на флешках | at rest, in use |
| `health.lab` | направления и результаты анализов | высокая (особая категория) | каналы бумага/e-mail/телефон, нет целостности | at rest, in transit |
| `pii.full_name`, `pii.birth_date`, `pii.phone`, `pii.email`, `pii.address` | анкеты пациентов | высокая (ПД, 152-ФЗ) | дублирование в Excel, отчёты, письма | at rest, in transit, in use |
| `pii.document` | паспорт, СНИЛС, ИНН | высокая | кража личности, мошенничество | at rest |
| `hr.salary`, `hr.personal` | ЗП, кадровые документы | высокая (ПД сотрудников) | 1С в файловом режиме - доступ у всех, кто открыл файл | at rest, in use |
| `fin.payment` | платежи, ID транзакций, карточные данные | высокая (PCI DSS) | двойной учёт Excel+1С, чек с ФИО | at rest, in transit |
| `corp.financial` | цены, реквизиты поставщиков, P&L | средняя (коммерческая тайна) | 1С в файловом режиме, отчёты по почте | at rest, in transit |
| `internal` | логи, служебная переписка | низкая | потеря целостности | at rest |

## 2. Реестр защиты

| Данные | В чём необходимость защиты | Инструменты защиты |
|---|---|---|
| Медкарты, диагнозы, заключения (`health.sensitive`) | особая категория ПД (152-ФЗ ст. 10) + врачебная тайна (323-ФЗ); сейчас лежит в открытом доступе на общем диске, доступен любому доменному пользователю | at rest: шифрование AES-256-GCM, доступ только лечащему врачу (ABAC), версионирование; in transit: TLS 1.2+; in use: маскирование в интерфейсе (не показывать лишние поля), аудит каждого обращения |
| Персональные данные пациентов: ФИО, ДР, контакты, адрес (`pii.*`) | 152-ФЗ: доступ только по целям обработки; сейчас дублируются в Excel, уходят в отчёты и письма целиком | at rest: шифрование хранилища (AES-256); in transit: TLS 1.2+ (портал, API, почта); in use: маскирование/инициалы в интерфейсах и чеках, DLP на исходящих каналах, согласие (ст. 9 - отдельные категории) |
| Паспорт, СНИЛС, ИНН (`pii.document`) | специальные документы - прямой инструмент кражи личности; хранить нужно минимум полей и как можно короче срок | at rest: шифрование + доступ только бухгалтерии и кадрам (RBAC), лимит срока хранения; in transit: TLS; in use: маскирование (только 4 последних цифры), аудит |
| Результаты анализов (`health.lab`) | особая категория ПД; сейчас ходят бумагой, e-mail и по телефону - каналы неконтролируемы | in transit: API лаборатории по HTTPS + OAuth2, чексаум/подпись сообщения; at rest: шифрование сканов, тег `health.lab_result`, доступ - только лаборант и лечащий врач; псевдоним в заказе (пациент идентифицируется псевдонимом, не ФИО) |
| Платежи, карточные данные (`fin.payment`) | PCI DSS: PAN хранить нельзя; сейчас чек печатается с полным ФИО, учёт дублируется Excel+1С | не хранить PAN - только ID транзакции от платёжного шлюза (tokenization); in transit: TLS, эквайринг через шлюз; at rest: шифрование 1С (серверный режим), доступ - кассир и бухгалтер; в чеке - инициалы |
| ЗП и кадровые документы (`hr.*`) | ПД сотрудников, 152-ФЗ; 1С в файловом режиме - файл открыл, все ЗП прочитал | 1С: файловый режим → серверный режим (контроль доступа на сервере); at rest: шифрование, RBAC «кадры/бухгалтер»; in transit: TLS; аудит доступа к `hr.salary` с алертами |
| Корпоративная финансовая информация: цены, реквизиты, P&L (`corp.financial`) | коммерческая тайна, конкурентный риск; сейчас отчёты уходят в личную почту целиком | in transit: TLS, DLP (блокировать исходящие письма с тегнутыми полями); at rest: шифрование, доступ по ролям; для руководства - агрегированные отчёты без ПД |
| Аналитические выгрузки (BI/ML) | при построении отчётов берутся «сырые» Excel с ПД - риск, что ПД окажется в отчёте/модели | псевдонимизация перед загрузкой в lake (`patient_id`); зоны хранилища по классам с отдельными ключами KMS; доступ к lake - только через теги; Data Lineage: видно, из чего собран отчёт |
| Бэкапы и копии | бэкап - полная копия всех ПД; украденный бэкап = украдены все данные | бэкапы шифруются отдельным ключом (отдельный от production), доступ к бэкапам - только IT, ротация ключей, хранение бэкапов не на том же диске |

## 3. Базовые инструменты защиты, которые нужно добавить

1. **KMS (управление ключами)** - единый источник ключей: генерация, хранение, ротация. Шифрование at rest - envelope encryption (мастер-ключ в KMS, data key для каждого хранилища/зоны). Алгоритм - AES-256-GCM (аутентифицированное шифрование, защита от подмены).
2. **TLS 1.2/1.3 на всех каналах** - порталы, API, почта, интеграции. Для API между системами - mutual TLS (каждая сторона предъявляет сертификат), чтобы исключить «чужой» сервис в сети.
3. **Токенизация платёжных данных** - PAN не попадает в контур, только токен/ID транзакции.
4. **DLP** - правила по тегам: исходящее письмо с данными `pii.*`/`health.*` блокируется или заменяется ссылкой на ЛК. Контроль и на конечных точках (USB, копирование на локальные диски).
5. **IAM (MFA + RBAC/ABAC)** - без MFA доступ к медкартам и ЗП; доступ к тегнутым данным только по тегу (ABAC), а не по «файлу открыл».
6. **Аудит/SIEM** - каждое обращение к тегнутым данным логируется (кто, что, когда); алерты на нетипичное (массовый экспорт, доступ ночью, запрос чужого пациента).

## 4. Автоматизированный контроль

* **Детектор тегов при загрузке** - пакет с данными, который пришёл в lake, сканируется до загрузки: ненайденные ПД-поля не попадают в хранилище (задача детально в Task 6).
* **DLP-правила** - срабатывают автоматически, без участия человека; отчёты о срабатываниях - в SIEM.
* **Алерты SIEM** - сценарии: массовое чтение чужих медкарт, экспорт > N записей за сессию, доступ вне графика.
* **Автоматическая проверка релизов** - пайплайн CI/CD перед релизом прогоняет тесты «релиз не сливает тегнутые данные» (скан ответов API и отчётов на наличие полей с тегами). Если тест падает - релиз не выпускается, алерт в мониторинг.
* **Регулярные проверки**: скан шаров общего диска на нешифрованные ПД-файлы, контроль сроков жизни сертификатов и ротации ключей KMS, проверка, что файловый режим 1С больше не включён.

## 5. Реестр программных и аппаратных средств

| Средство | Тип | Состояние данных | Что делает |
|---|---|---|---|
| KMS (например, Vault) | ПО | at rest | мастер-ключи, envelope encryption, ротация |
| HSM (опционально, для корня ключей) | железо | at rest | мастер-ключи не покидают аппаратный модуль |
| AES-256-GCM (библиотеки шифрования) | ПО | at rest, in use | шифрование БД, файлов lake, бэкапов |
| Шифрование томов (LUKS / BitLocker) | ПО/железо | at rest | защита при физической потере диска |
| TLS 1.2+ / mTLS (серверы, шлюзы) | ПО | in transit | все каналы: портал, API, почта, ККМ, 1С |
| Сервис токенизации (платёжный шлюз) | ПО | at rest, in transit | PAN не хранится в контуре |
| DLP-система (почта, конечные точки) | ПО | in transit, in use | блокировка исходящих ПД по тегам |
| SIEM (логи + алерты) | ПО | at rest | аудит обращений, сценарии аномалий |
| IAM: AD + MFA, RBAC/ABAC | ПО | in use | аутентификация и авторизация по тегам |
| Файрвол / IPS периметра | ПО/железо | in transit | сегментация: lake и медкарты не видны из офисной сети напрямую |
| Сервер 1С (серверный режим) + БД с шифрованием | ПО | at rest | замена файлового режима, контроль доступа |
| Бэкап-сервер с отдельным ключом шифрования | железо/ПО | at rest | резервные копии, изолированное хранение |
| Шифрование рабочих станций (BitLocker) + DLP-агент | ПО/железо | at rest, in use | защита данных на ноутбуках сотрудников |

## Вывод

Сначала - классификация и теги (без них шифрование «всего подряд» не даёт контроля доступа). Затем базовый набор: KMS + TLS + IAM + DLP + аудит. И автоматический контроль: детектор при загрузке, DLP, алерты SIEM и проверка релизов в CI/CD - чтобы защита не деградировала по мере роста числа филиалов и сотрудников.
