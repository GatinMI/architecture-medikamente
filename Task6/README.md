# Задание 6. Движок классификации данных перед загрузкой в аналитическое хранилище

Диаграмма C2 - `c2-classification-engine.drawio`.

## 1. Движок классификации

**Проблема.** Данные в аналитику приходят пакетно из нескольких источников (1С серверный режим, исторические Excel/CSV, API CRM и лаборатории) с двумя свойствами, которые ломают «просто загрузить в lake»:

1. **Структуры меняются** - новые поля, переименованные столбцы, другой формат дат. Схема на входе нестабильна.
2. **Данные не размечены** - какое поле ФИО, а какое «имя пациента для аналитики», никто заранее не гарантирует: источники разные, ответственность за данные расплывчатая.

Поэтому между источниками и хранилищем стоит **промежуточный слой**, который каждый пакет принимает, разбирает, размечает и решает, куда и в каком виде он может попасть. Слой не пропускает «сырые» данные напрямую в зоны, которыми пользуются аналитики.

### Конвейер (пакетный, по расписанию или по событию от источника)

1. **Ингест (Kafka).** Коннекторы по источнику. Пакет получает ID, метаданные источника, схему-версию. Канал по партициям источника - это и есть механизм масштабирования по входу.
2. **Валидация схемы (schema registry).**
   * У каждой темы/источника - зарегистрированная версия схемы. Новый пакет сверяется с последней зарегистрированной версией.
   * **Tolerant reader**: дополнительные неизвестные поля - не ошибка, они сохраняются в `__extra` (JSON) и помечаются для ревью; пропавшее обязательное поле или изменение типа - ошибка.
   * Совместимая новая версия (только добавления полей) регистрируется автоматически. Несовместимое изменение - пакет в карантин, алерт, новая версия схемы регистрируется человеком (владелица источника). Это и есть ответ на «структурные изменения на входе»: пайплайн не падает, а **паркует** и требует решения.
3. **Классификатор.** Каждому полю пакета присваивается тег класса (те же, что в Task1/Task3: `pii.*`, `health.*`, `hr.*`, `fin.*`, `corp.financial`, `internal`) + уровень уверенности confidence.
   * **Правила** (детерминированные, объяснимые): словарь имён полей и их алиасов (`full_name`, `ФИО`, `name_pat` → `pii.full_name`), regex на форматы (паспорт, СНИЛС, ИНН, телефон, e-mail, карта), словарь медицинских терминов и кодов диагнозов → `health.sensitive`.
   * **ML-детектор** (auxiliary): на содержимом значений (не только в имени поля) - NER для ФИО, адресов, дат рождения, классификация текста заключений. Срабатывает, когда поле «тихо» переименовали, а правило по имени молчит.
   * Поле получает тег с **наибольшим** уровнем чувствительности среди сработавших детекторов (принцип «worst case wins») - ошибка «вниз» (сказать, что чувствительное поле обычное) дорого, ошибка «вверх» дёшева: данные просто лягут в более защищённую зону.
   * **Не распознано** - не «internal», а `unknown`. `unknown` - это сигнал, а не категория.
4. **Policy-движок.** По тегам решает маршрут пакета/поля:
   * `pii.*`, `fin.*`, `hr.*` → зона restricted; `health.*` → зона high-sensitivity (дополнительное шифрование, отдельные ключи);
   * перед загрузкой в аналитические зоны - **псевдонимизация**: ФИО/контакты/даты замещаются на `patient_id` (токен) из таблицы соответствия, которая хранится отдельно, в high-sensitivity зоне, и не выдаётся аналитике;
   * `unknown` или confidence ниже порога (например 0.8) → **карантин (hold)**: пакет не попадает в доступные аналитику зоны, падает в каталог на ревью. Никогда не «пропустить по умолчанию».
5. **Каталог данных (lineage).** Для каждого поля в lake пишется запись: источник, схема-версия, тег, кто классифицировал (правило/ML/человек), confidence. Это и Data Lineage на уровне полей, и **обучающее датасет** для калибровки детекторов (ревью в карантине = размеченные примеры).
6. **Аудит.** Каждое решение (тег, маршрут, карантин, ручное ревью) - событие в SIEM. Аномалии: пакет с аномально высокой долей `health.sensitive` из источника, который их обычно не присылает; рост доли `unknown` (дрейф схемы); попытка доступа к токен-таблице.

## 2. Слои в хранилище

Организация lake - по глубине обработки, с зонами чувствительности внутри:

| Слой | Содержимое | Доступ | Охрана |
|---|---|---|---|
| **bronze (raw)** | исходные пакеты без изменений, 30 дней (после этого - в холодный архив) | только пайплайн | шифрование at rest; доступ извне запрещён - сырые ПД не должны уходить в руки аналитиков даже «на один раз» |
| **silver (clean)** | нормализованные данные, **с тегами**, зонировано: `open`, `restricted (pii.*/fin.*/hr.*)`, `high-sensitivity (health.*)` | open - все с ролью аналитика; restricted - по тегу (ABAC); high-sensitivity - только заявленные ML-пайплайны, не интерактив | шифрование at rest: у каждой зоны **свой ключ** в KMS - компрометация ключа одной зоны не открывает другую; high-sensitivity шифруется полевым уровнем даже внутри silver |
| **gold (аналитика)** | псевдонимизированные сводные данные для BI/ML/LLM | аналитики и модели; токены `patient_id` без таблицы соответствия | в gold нет ПД по определению - только псевдонимы и агрегаты |

Ключевое решение: **зона чувствительности - свойство слоя, а не таблицы в нём** (зоны внутри silver). Это значит, что когда появится новый класс данных, он не требует перестройки хранилища - нужна новая зона с новым ключом и новым правилом доступа.

Дополнительные меры (помимо слоёв): TTL bronze 30 дней (минимизация данных - сырые ПД не живут вечно); удаление по запросу пациента (152-ФЗ) - процедура, которая проходит по lineage: каталог знает, в каких слоях и партициях живёт пациент, удаление идемпотентно по `patient_id`; токенизация необратима без специальной церемонии (таблица соответствия - отдельный артефакт с собственным контролем доступа).

## 3. Метрики классификации

| Метрика | Как измеряется | Зачем (оптимизация) |
|---|---|---|
| **Recall по `health.sensitive`** (главная) | карантины и выборочные ручные проверки против «истины»; пропущенное - находит аудит (доступ, где не ждали) | пропуск чувствительного поля в gold - инцидент по определению. Низкий recall → новые правила/термины, снижение порога ML-детектора |
| **Precision по тегам** (доля полей, помеченных зря) | ревью карантина: доля «ложных тревог» | завышенный precision-cost → поля живут в дорогих зонах, ML-модели получают меньше данных. Высокая доля ложных → ужесточить правила, добавить алиасы-исключения |
| **F1** сводная, разбивка по классам | еженедельный срез по размеченному ревью-датасету | одна цифра для трека здоровья классификатора; деградация F1 - триггер переобучения |
| **Доля `unknown`** (coverage = 1 − unknown) | доля полей в новых пакетах без тега | рост = структурный дрейф на входе: кто-то изменил схему молча. Триггер на ревью схемы источника, не на детектор |
| **Доля карантина** | пакеты/поля в hold vs. всего | резкий рост - либо дрейф (см. выше), либо источник начал присылать новое; долгий карантин = процесс ревью стал бутылкой → нанять/перераспределить |
| **Время от пакета до gold (latency) и throughput** | метрики пайплайна | SLA для аналитики; деградация → масштабирование (раздел 4) |
| **Lineage-полнота** | доля полей в silver/gold с полной записью (источник, тег, версия схемы, кто классифицировал) | без lineage не выполнить удаление по запросу пациента и не расследовать инцидент; цель 100% |

Замыкание петли: ревью карантина размечает примеры → это обучающий датасет для ML-детектора → детектор учится на ошибках → доля `unknown` и карантина падает. Система улучшает себя по мере работы, а не «настраивается один раз».

## 4. Масштабируемость

* **По входу:** Kafka, партиции по источнику (и внутри источника - по `patient_id`, чтобы один пациент не размазывался по партициям). Новые филиалы = новые источники = новые партиции/коннекторы, конвейер не меняется.
* **Конвейер stateless:** валидация, классификатор, policy - функции без состояния, масштабируются горизонтально добавлением реплик; пакетный режим на Spark/стриминг - переключение режима, а не переписывание. Состояние - только в каталоге (БД) и KMS, и оба масштабируются вертикально/кластером.
* **Хранилище:** sharding silver/gold по `patient_id` + зонирование по чувствительности (отдельные физически разделённые хранилища/кейspaces с отдельными ключами - урон по одной зоне не открывает остальные). Рост данных = добавление шардов, без рефакторинга схемы.
* **Пользователи:** доступ к gold - через витрины (материализованные своды), а не прямые запросы по silver: 100 аналитиков бьют в своды, а не в защищённые слои. ML-обучение берёт данные через те же токены, что и BI - одна точка контроля.
* **Пятикратный рост** по заявке бизнеса - это рост партиций и шардов + реплик конвейера; архитектура линейно масштабируется по всем трём осям (вход, обработка, хранение), без «большого дня» на расширение.

Единственная нелинейная точка - **ревью карантина** (люди). Меры: порог confidence калибруется так, чтобы в карантин падало < 5% полей; автопропуск карантина для полей, которые 100 раз классифицировались человеком одинаково (правило «опыта»); и если доля карантина всё равно растёт - это бизнес-сигнал, что источник нужно заставить присылать схемы (schema-on-write).
